# Implement

Execute an approved spec without reopening design decisions. If you find
yourself wanting to decide something, that is a signal the spec is incomplete —
log it, do not quietly decide it.

## 1. The gate, first, always

```
harness gate <id>
```

Non-zero means stop and report why. Do not work around it, do not implement
"just the safe part". The three failure modes and what each means:

- **not approved** — a human has not signed off. Ask them to.
- **hash mismatch** — approved once, then edited. The contract changed; it
  needs re-approving.
- **another spec is active** — one at a time. Offer `harness pause <other>`.

## 2. Context pack

Dispatch `context-packer` for the frameworks this spec touches. It pins
versions from the lockfiles and distils the API surface into one small file, in
its own context — so forty thousand tokens of documentation never reach yours.

If it reports that documentation was unreachable, that is an allowed outcome
and it will have left an `[offline]` marker in `notes.md`. Do not retry, and do
not quietly proceed as though the pack existed: the marker is what tells anyone
later which code was written blind.

## 3. Plan

Read the approved spec and the code *as it is today* — not as it was when the
spec was written. Write `plan.md`: ordered tasks, the package each belongs to,
files touched, risks, and **the verification command for each task**. That last
field is what makes the plan executable instead of decorative.

**Task zero is always the same:** relocate `acceptance.*` from the spec folder
into the target package's test directory. Choosing that target is the moment
the plan commits to a package, which is why it could not happen while shaping.

## 4. Build, one task at a time

For each task: implement → run its verification command → fix → next.

As each acceptance test body is filled in, **remove its pending marker**. The
markers are the progress counter; `harness status` reports `4/7 criteria live`
from them, so leaving a marker on finished work makes the number lie.

Log every deviation in `notes.md` as you go. When you hit an edge case the spec
did not cover, pick the conservative option, write down what you picked and
why, and keep going. Do not stop to ask unless proceeding would be unsafe.

## 5. Verify

```
harness verify --affected
```

Scoped to the packages you touched plus everything that depends on them. Run it
after each task, not once at the end.

Loop until green, **but with a budget**: if a check has failed three times and
you are not converging, stop and report what you tried. A long thrash against a
test that was never going to pass costs more than an early admission.

## 6. Adversarial review

Dispatch `diff-reviewer`. It did not write this code, which is the whole
reason it can judge it: you are inclined to believe your own implementation
works. Address its findings or record why you disagree in `notes.md`.

## 7. Close

- Every tier A and B criterion green, zero pending markers left.
- **Tier C criteria go to the human as a checklist.** Never tick them yourself
  — a model grading its own subjective quality always awards itself a pass.
- Deviations in `notes.md` resolve one of three ways: fixed, or they amend the
  spec (which breaks the hash and needs re-approval, correctly), or they become
  new `harness inbox add` items.

Then set the spec to `done` and report: what shipped, what deviated, what went
back to the inbox.
